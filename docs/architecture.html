On-device voice assistant · Android

Google Voice Pipeline — speech in, speech out, no cloud.

You speak; your voice is transcribed, answered by an on-device LLM, and spoken back — every stage runs on the phone's own CPU/NPU. Once the models are downloaded it works in airplane mode. Verified end-to-end on a Pixel 10 (Tensor G5).

01

The pipeline

A single conversational loop. The microphone streams PCM; each stage hands off to the next; a near-duplicate filter and a speech sanitizer sit between the model boundaries. Barge-in listens the whole time. Hover a stage to see the class that owns it.

Turn-taking

Barge-in

BargeInController cancels the in-flight LLM and stops TTS when the user speaks over the assistant — 150 ms debounce plus a ~1.2 s TTS-onset grace to reject the assistant's own echo.

Memory

Rolling context

Each turn sends the system message plus the last 5 exchanges plus the new turn. Transcripts and messages are persisted locally in Room.

Echo control

Input gating

STT input is gated while TTS plays so neither recognizer transcribes the assistant's own voice. A 400 ms hangover covers the echo tail after speech ends.

02

Swappable engines

Every model boundary is an interface with more than one implementation, chosen at runtime. The LLM resolves down a three-tier fallback chain; STT routes between two engines per session. The pipeline always runs — worst case, on the stub.

LLM · LlmOrchestrator → fallback chain

1

MediaPipeLlmEngine

primary · any device
MediaPipe LLM Inference (LiteRT) · tasks-genai:0.10.27

Runs downloaded .task models (Qwen / Phi / Gemma) directly — the same runtime as Google's AI Edge Gallery. A fresh session per turn re-prefills history today; a persistent KV-cache session is on the roadmap.

2

MlKitLlmEngine

secondary · AICore
Gemini Nano via ML Kit GenAI Prompt · genai-prompt:1.0.0-beta2

Used only where ML Kit Prompt Feature 636 is provisioned (e.g. Pixel 10 Tensor G5). 606-FEATURE_NOT_FOUND elsewhere is a device-provisioning state, not an app bug.

3

StubLlmEngine

fallback · always
Canned responses

Keeps the pipeline runnable when no model is present. Wraps its output in TextCompleted so the ViewModel's collection logic is unchanged.

User override

PipelineMode

AUTO — MediaPipe (if downloaded) → AICore → offer download → stub.
MEDIAPIPE — only the selected LiteRT model, never AICore.
AICORE — only Gemini Nano; unavailable if Feature 636 isn't provisioned.

STT · SttRouter

Two recognizers

SherpaSttEngine (default) — streaming Zipformer, VAD-gated, finalizes on SPEECH_END.
MlKitGenAiSttEngine (experimental) — ML Kit GenAI ASR on AICore, fed the same PCM via an fromPfd pipe. Prefers Basic (SODA) over Advanced to avoid contending with Gemini Nano.

03

Model catalog

Models aren't bundled — they download on-device (or via adb push to /data/local/tmp). The LLM is user-selectable in Settings; the choice persists in DataStore. Gated models need a Hugging Face token, sent as a Bearer header to huggingface.co only.

06

What we learned

The hard problems — the "what we learned" slides. On-device is not a uniform target; the accelerator is shared; and turn-taking is still the frontier.

Device-specific audio capture

Problem
The Pixel 10's VOICE_COMMUNICATION + AEC/NS/AGC chain delivered signal ~20–50× too quiet — loud speech peaked ~0.013 RMS against the 0.027 VAD bar, so there were no transcripts at all.
Fix
A fixed 8× software gain stage in AudioCapture, restoring usable levels for the VAD and recognizer.
Takeaway
On-device audio isn't uniform across handsets; the gain is a per-device constant that may need retuning elsewhere.

AICore contention

Problem
Running ML Kit GenAI Advanced ASR and Gemini Nano simultaneously — both on AICore — starved each other; Nano slowed from ~2 s to >6 s and replies got cancelled.
Fix
Prefer Basic (on-device SODA) STT, which doesn't contend with Nano; use Advanced only when the LLM is off AICore (PREFER_ADVANCED = false).
Takeaway
The on-device accelerator is a shared, finite resource — you schedule around it.

Turn-taking is the frontier

Problem
Today's VAD and barge-in are energy heuristics, not models — tuned thresholds, not understanding.
Fix
A fully-on-device, Deepgram-Flux-style path: neural VAD → eager endpointing → semantic end-of-turn. The retract plumbing (cancelResponse() + llmJob.cancel()) already exists.
Takeaway
A credible on-device approximation of cloud-Flux quality is within reach in 2026.
07

Roadmap

Toward model-based turn-taking, in rough order of leverage. The building blocks already ship — the app carries both the ONNX and LiteRT runtimes.

01Neural VAD

Replace the energy SileroVad with real Silero VAD ONNX (~2 MB, bundled with Sherpa) behind the same interface. Highest bang-for-buck.

02Eager end-of-turn event model

Flux-style eager → resume → commit: start the LLM on a medium-confidence endpoint and cancel if the user resumes. Architecture only, no new model.

03Semantic end-of-turn

Run an on-device turn model (e.g. Smart Turn v2/v3, Wav2Vec2-based) at candidate endpoints instead of the fixed 1.5 s silence timer. The actual Flux-like capability.

04Reference-based AEC

Feed the TTS PCM as the echo reference (e.g. WebRTC AEC3) for robust speakerphone barge-in on devices with worse hardware AEC than the Pixel 10.

05Adaptive noise-floor threshold

Track the noise floor so the capture gain and barge-in bar stop needing per-device constants.

06Persistent KV-cache LLM session

Keep a persistent MediaPipe session that retains the KV cache and feeds only the new user turn, flattening latency regardless of conversation depth.
